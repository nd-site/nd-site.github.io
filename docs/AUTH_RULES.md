### Architectural Principle (Mandatory Rule)

**English:**
> *"Every internal relationship to a user MUST reference the immutable CodeID. User-facing attributes such as NDID, email, name, avatar, or profile data MUST be resolved from the canonical user record using CodeID and MUST NOT be used as the canonical relationship key."*

**Tiếng Việt:**
> *"Mọi quan hệ nội bộ tới tài khoản người dùng bắt buộc phải tham chiếu bằng CodeID bất biến. Các thông tin người dùng có thể thay đổi như NDID, email, tên, avatar hoặc dữ liệu hồ sơ phải được trích xuất từ user record canonical thông qua CodeID và không được sử dụng làm khóa liên kết canonical."*

## 1. Canonical Identifiers

### 1.1 CodeID (Canonical Immutable Identity)
CodeID is the permanent, immutable, unique business identifier of every account.

| Property | Canonical Specification |
|---|---|
| **Role** | Primary Account Identity, Firestore User Key (`users/{CodeID}`), Foreign Key |
| **Firebase Auth UID** | **Identical to CodeID** (`Firebase Auth UID === CodeID`) |
| **Format** | Decimal string, zero-padded 4 digits (`0000` to `9999`), expanding to 5+ digits (`10000`, `10001`, ...) |
| **Generation** | Server-side only via Firestore transaction on atomic counter `counters/code_ids` |
| **Consumption** | Consumed upon allocation. If registration fails, CodeID is **never recycled**. Sequence gaps allowed. |
| **Client Generation** | **ABSOLUTELY FORBIDDEN** (No `Math.random()`, `Date.now()`, or client counter) |

### 1.2 NDID (User Handle)
NDID is a user-facing, unique human-readable username.

| Property | Canonical Specification |
|---|---|
| **Role** | Login identifier and public handle |
| **Mutability** | Mutable attribute. Can be changed by user (via server API) or Admin/Owner |
| **Reservation** | When changed, old NDID is reserved for 30 days before becoming available to others |
| **Validation** | User-facing input forms apply regex `/^[a-zA-Z0-9_.]+$/` (lowercase, digits, `_`, `.`) |
| **Stored Values** | Raw string stored in DB is preserved without stripping or sanitizing |
| **Prohibitions** | **NEVER convert to fake email. NEVER auto-prepend `@`. NEVER use as foreign key.** |

### 1.3 Email
Email is an independent user attribute used for login, notifications, and recovery.

| Property | Canonical Specification |
|---|---|
| **Role** | Secondary login credential, password recovery, verification, security notifications |
| **Independence** | Independent of NDID. Never generated from NDID. |
| **Mutability** | Mutable via 2-step server-side verification process |
| **Prohibitions** | **NEVER use as canonical foreign key.** |

### 1.4 Firebase Auth UID
Firebase Auth UID is identical to CodeID (`auth.uid === CodeID`). All Firebase Custom Tokens generated by the trusted backend mint `uid = CodeID`.

## 2. Password & Credential Security

### 2.1 Password Storage
- Plaintext password storage is **ABSOLUTELY PROHIBITED** (Legacy fields like `registeredPassword` are deprecated and scheduled for deletion).
- Passwords MUST be hashed server-side using **bcrypt** (cost ≥ 10) or **Argon2id**.
- The hash is stored exclusively in `users/{CodeID}/private/security.passwordHash`.
- The hashing algorithm version is tracked via `users/{CodeID}/private/security.passwordVersion`.

### 2.2 Prohibitions
Passwords (plaintext or hash) MUST NEVER appear in:
- Client-readable Firestore documents (`users/{CodeID}`)
- `localStorage`, `sessionStorage`, cookies, or browser caches
- URL query parameters or hash fragments
- `console.log()` or error traces
- CardID images, downloaded assets, or clipboard operations

## 3. Login & Authentication Flow

```
1. Client submits { identifier (NDID or Email), password } to backend Cloud Function
2. Backend resolves identifier -> CodeID using server-only mapping collections (ndids/ or emails/)
3. Backend loads users/{CodeID}/private/security
4. Backend checks users/{CodeID}.status:
   - If 'locked': reject with 403 (Lockout active)
   - If 'disabled' or 'banned': reject with 403
   - If 'pending': reject with 403
5. Backend verifies passwordHash against submitted password
6. On Failure:
   - Increment failedLoginAttempts atomically in private/security
   - If failedLoginAttempts >= 5: set users/{CodeID}.status = 'locked', record lockedAt
   - Return generic 401 error: "Thông tin đăng nhập không chính xác."
7. On Success:
   - Reset failedLoginAttempts = 0
   - Update users/{CodeID}.lastLoginAt = serverTimestamp()
   - Mint Firebase Custom Token with uid: CodeID
   - Return { customToken, userProfile } to client
8. Frontend calls signInWithCustomToken(auth, customToken)
9. Firebase Auth session is established with request.auth.uid === CodeID
```

## 4. Roles, Permissions & Owner Bootstrap

### 4.1 Role Hierarchy
- `role`: `"user"` or `"admin"`
- `adminLevel`: `null` (for regular users), `"admin"`, or `"owner"` (for admins)
- **Owner** is the supreme authority. Only Owner can grant/revoke Admin status or delete accounts.
- **Admin** cannot self-promote, cannot grant Admin to others, and cannot modify or delete the Owner.

### 4.2 Owner Bootstrapping
- The first Owner account is **NEVER hardcoded** in frontend code, environment variables, or config files.
- The first Owner is bootstrapped via a trusted/manual Firestore write in the Firebase Console or via a one-time trusted Admin SDK script.

### 4.3 Client Enforcement Boundary
- Frontend components (`ProtectedRoute`, `AdminRoute`, `OwnerRoute`) are strictly **convenience / UX aids**.
- Actual security enforcement is executed exclusively by **Firestore Security Rules** and **Cloud Functions**.

## 5. Account Status & Server Lockout

### 5.1 Status State Machine
- `active`: Normal functioning account.
- `pending`: Awaiting initial email verification.
- `locked`: Automatically triggered after **5 consecutive failed password attempts**.
- `disabled`: Temporarily suspended by Admin or Owner.
- `banned`: Permanently or duration-banned by Admin or Owner.

### 5.2 Server-Side Atomic Lockout
- `failedLoginAttempts` is tracked in `users/{CodeID}/private/security`.
- Increment is atomic via backend transaction or `FieldValue.increment(1)`.
- Client cannot clear or bypass lockout by refreshing, clearing browser data, or manipulating requests.
- Account is unlocked upon successful password recovery via verified email or manual Owner review.

---

## 6. Account Recovery & Verification

### 6.1 Recovery Channels
1. **Verified Email OTP / Link:** Primary recovery mechanism. Cryptographic token generated server-side with 15-minute TTL.
2. **Linked Google Account:** Verified via Google ID Token on trusted backend.
3. **Owner / Admin Manual Intervention:** Reserved for disputed recovery cases.
4. **AI-Assisted Evaluation (Future):** AI evaluation is strictly advisory and can **never** be the sole proof of ownership.

### 6.2 Anti-Enumeration Recovery
Recovery requests return uniform responses regardless of whether the submitted identifier exists in the database.

## 8. Google Identity Linking Invariants (Phase 01-C4)

1. **Provider Identity vs Attributes:**
   - Provider mapping is keyed strictly by Google Subject ID (`sub` / provider `uid`) in server-only collection `google_identities/{googleSubjectId}`.
   - Google email is an informative attribute, NOT the unique mapping key.
2. **Strict 1-to-1 Mapping:**
   - A Google account can be linked to at most ONE canonical `CodeID`.
   - Re-linking the same Google account to the same `CodeID` is idempotent (`noOp: true`).
   - Linking a Google account already mapped to another `CodeID` is rejected with HTTP 409 (`GOOGLE_IDENTITY_ALREADY_LINKED`). Automatic account merging is **STRICTLY PROHIBITED**.
3. **Lockout Prevention:**
   - Unlinking Google is blocked if the account has no registered password (`users/{CodeID}/private/security.passwordHash`).
4. **Zero Client Authority:**
   - Client read and write on `google_identities/` are completely denied (`allow read, write: if false;`).
   - Client cannot set `users/{CodeID}.googleEmail` or `users/{CodeID}.googleSubjectId` directly. All mutations must occur via Cloud Functions with ID token verification.

## 9. Account Recovery & Lockout Invariants (Phase 01-C5)

1. **Backend-Generated One-Time Codes:**
   - Recovery codes are generated strictly server-side using cryptographic randomness (`crypto.randomInt(100000, 1000000)`).
   - Raw codes are **NEVER stored in Firestore**. Only the SHA-256 hash is saved in `users/{CodeID}/private/recovery`.
   - Codes expire strictly after 15 minutes (`expiresAtMs`).
2. **Verified Email Requirement:**
   - Account recovery via email requires a verified email address (`emailVerified: true` or verified recovery email).
   - Unverified accounts cannot receive recovery codes; the system returns generic 200 OK without generating codes.
3. **Rate Limiting & Cooldown:**
   - A minimum 60-second cooldown is enforced between recovery code requests per account to prevent spam and denial of wallet attacks (HTTP 429).
4. **Brute-Force Protection:**
   - Maximum 5 attempts allowed per recovery session (`maxAttempts: 5`).
   - Every incorrect submission increments `attemptCount` atomically. Upon the 5th failed attempt, status is updated to `'locked'`, terminating the attempt.
5. **Single-Use Password Reset Token:**
   - Successful code verification invalidates the code immediately (`codeHash: null`) and issues a single-use 32-byte hex `resetToken` with 10-minute TTL.
   - Using the `resetToken` to reset password immediately transitions recovery status to `'consumed'` and wipes `resetTokenHash`.
6. **Automatic Account Unlock Flow:**
   - Account lockout resulting from 5 consecutive failed login attempts can only be resolved via verified recovery or manual Owner action.
   - Successful password reset via verified recovery automatically:
     - Clears `lockedAt` and `lockReason` in `private/security`.
     - Resets `failedLoginAttempts = 0`.
     - Sets user document `status = 'active'` in `users/{CodeID}`.
     - Revokes all active user sessions across all devices via `auth.revokeRefreshTokens(CodeID)`.
7. **Comprehensive Audit Trail:**
   - Every step of the recovery lifecycle emits immutable audit events to `security_events`: `recovery_requested`, `recovery_code_verified`, `recovery_failed`, `password_reset`, `account_unlocked`.
   - Audit events MUST NOT contain raw secrets, passwords, or plaintext OTPs.

## 10. Sessions & Trusted Devices Invariants (Phase 01-C6)

1. **Subcollection Isolation:**
   - Active sessions are stored under `users/{CodeID}/sessions/{sessionId}`.
   - Trusted devices are stored under `users/{CodeID}/devices/{deviceId}`.
   - Both subcollections are strictly denied to direct client access via Firestore rules (`match /sessions/{document=**} { allow read, write: if false; }`, `match /devices/{document=**} { allow read, write: if false; }`).
2. **Identity Invariant Enforcement:**
   - All session and device operations require a valid Firebase Auth ID token.
   - Backend extracts `CodeID` via `verifyIdToken(idToken)` and enforces `UID === CodeID`.
   - Cross-user enumeration or manipulation is structurally blocked.
3. **Zero Secret Storage:**
   - Device fingerprints are hashed using SHA-256 (`deviceFingerprintHash`). Raw fingerprint secrets are NEVER stored or returned to clients.
4. **Fail-Closed Revocation Lifecycle:**
   - Password reset immediately calls `revokeAllSessions(db, codeId, 'password_reset')` and `auth.revokeRefreshTokens(codeId)`.
   - Password change calls `revokeOtherSessions(db, codeId, null, 'password_changed')` and `auth.revokeRefreshTokens(codeId)`.
   - Account lockout calls `revokeAllSessions(db, codeId, 'account_locked')` and blocks session registration.
5. **Privacy & Masking:**
   - Network IPs are sanitized at the subnet level (`113.190.234.*`).
   - Timestamps are projected in relative Vietnamese strings to prevent timing analysis.

## 11. Authorization, Production Hardening & Legacy Auth Cutover Invariants (Phase 01-C7)

1. **Role Model & Privilege Governance:**
   - Canonical Roles: `role: 'user' | 'admin'`.
   - Admin Levels: `adminLevel: null | 'admin' | 'owner'`.
   - Regular users have `role: 'user'`, `adminLevel: null`.
   - Administrators have `role: 'admin'`, `adminLevel: 'admin'`.
   - System Owners have `role: 'admin'`, `adminLevel: 'owner'`.
2. **System Owner Protection:**
   - System Owner CANNOT be promoted or demoted by normal users or administrators.
   - First Owner bootstrap is preserved from existing database authority.
   - Zero frontend hard-coding of admin or owner identities (no hardcoded emails or UIDs in client or rules).
   - Zero-Owner Lockout Prevention: The system strictly blocks demoting the last remaining active System Owner.
3. **Privilege Escalation Prevention:**
   - Normal users cannot alter `role`, `adminLevel`, `status`, or `codeId` under any circumstance.
   - Administrators cannot grant/revoke admin or owner privileges, nor self-promote.
   - Only an active System Owner can grant or revoke administrative roles via server-side Cloud Function (`updateUserRole`).
4. **Firestore Rules Hardening:**
   - Direct client user creation is completely disabled (`allow create: if false;`).
   - Direct client user deletion is completely disabled (`allow delete: if false;`).
   - Self-update on `users/{userId}` enforces strict immutability of `codeId`, `role`, `adminLevel`, `status`.
   - Admin update via client Firestore SDK is restricted to non-privileged attributes on non-owner users.
   - Server-only collections and subcollections (`private/**`, `sessions/**`, `devices/**`, `counters/**`, `ndids/**`, `emails/**`, `google_identities/**`) deny all client read/write.
   - Security audit log (`/security_events/**`) read is restricted to verified Admins; write is completely denied to clients.
5. **Legacy Auth Cutover (Complete Decommissioning):**
   - Fake email addresses (`${ndid}@ndsite.web.app` or `${ndid}@ndsite.id`) in authentication code are 100% eliminated.
   - Plaintext `registeredPassword` in client auth code is 100% eliminated.
   - Client-side `Math.random()` OTP generation is 100% eliminated.
   - Unverified fallback writes to `localStorage.nd_user` are 100% eliminated.
   - Canonical Auth is the primary and ONLY authentication mechanism for the entire application.
6. **Route Guards as UX Layer Only:**
   - Client-side route guards (`requireAuth`, `requireRole`, `requireAdmin`, `requireOwner`) exist purely for UX convenience and page flicker prevention.
   - Server-side Firestore Security Rules and Cloud Functions enforce authoritative security boundaries.
